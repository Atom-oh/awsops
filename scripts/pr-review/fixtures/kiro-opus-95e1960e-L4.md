## MAJOR

1. Marker uniqueness is counted over tool output and quoted content, unlike body counting — a correct report that reproduces the marker is discarded and escalates to a repo-wide forced FAIL.
In panel_report_valid (lib.sh), the awk rule /^REVIEW_COMPLETE:/ { markers++ } runs unconditionally: it is outside the in_tool gate and is not subject to the inline-code/quoted-string masking that was carefully added for tool-status detection (gsub(/[^]*|"…"|'…'/, "", status) only builds status, never affects the marker rule). Consequences:
- A finding that quotes the contract at line start — a fenced block containing REVIEW_COMPLETE: L4, or a markdown blockquote > REVIEW_COMPLETE: L4 (the >  is stripped first, so it becomes a line-start match) — yields markers == 2 → cell invalid.
- Any tool dump whose lines begin with the marker string is counted the same way, even though the very next rule deliberately excludes tool lines from lines.

Because run-panel.sh now treats every one of the 12 cells as required (lens_count -lt TOTAL_MODELS → coverage-severe.flag), and synthesize.sh turns that flag into an unconditional VERDICT: FAIL, one reviewer quoting the marker blocks the whole PR after two attempts. This is most likely to trigger on PRs that touch this pipeline itself, i.e. the failure mode is self-inflicted and reported as "incomplete AI review coverage" rather than as a validator artifact. The masking already exists for tool headers; the same treatment (or restricting the count to lines outside in_tool/quoted spans) should apply to the marker.

**2. Kiro completion detection hard-depends on undocumented, version-specific CLI presentation, with no real capture behind it and no degradation path.**
The validator's body counting only resumes at a line whose prefix is exactly >  (assistant = sub(/^> /, ""); if (assistant) in_tool = 0), and tool regions are entered on the literal spellings (using tool: …), ✓ Successfully , Summary: N operations processed. Nothing in the base documents any of these (grep for using tool: / assistant prefix finds only the pre-existing --wrap never comments), and test_review_completion.py states its own fixtures are "excerpts, not a full CLI capture" with the prefix marked merely "Observed". If a kiro-cli build omits/changes the >  prefix after tool use, in_tool never resets, lines stays 0, and **all 8 kiro cells fail every run** → coverage-severe.flag → every PR permanently BLOCKED with a message pointing at coverage, not at the parser. The fixtures cannot catch this because they encode the assumption. Given the new all-12-required policy removed the previous warn-only cushion, this needs either a fallback (e.g. accept a marker-terminated report when no tool region was ever detected) or an explicit version pin/verification note next to the parser.

**3. The codex path gets none of the tolerance added for kiro, and no fixture covers real codex trailer output.**
For non-kiro slots the awk applies no whitespace trimming, no > /tool masking, and no footer allowance. Therefore an indented marker line, a trailing space after REVIEW_COMPLETE: L4, or any line the codex harness prints after the model's final line (usage/token/session trailer) makes last != marker and invalidates all 4 codex cells → forced FAIL. The fake CLI in test_review_completion.py prints only the model body for codex, so the "codex stdout ends exactly at the model's last line" assumption is asserted nowhere. I could not verify real codex exec stdout from this checkout — flagging it as an unverified assumption with a fail-closed, repo-wide blast radius, and recommending at minimum the same trim (sub(/^[ \t]+/,""); sub(/[ \t]+$/,"")) on both paths.
